# Command runbook

This is the human-readable command surface. It will eventually be generated from the same canonical registry used by the CLI, MCP adapter, and machine-readable schemas.

## Development

| Command | Meaning |
| --- | --- |
| `uv sync --extra dev` | Create/update the environment and install development tools. |
| `uv run harness doctor` | Report harness and local prerequisite information. |
| `uv run harness validate` | Check the repository's required structure. |
| `uv run pytest` | Run unit tests. |
| `uv run ruff check .` | Run static lint checks. |
| `uv run mypy src` | Run strict type checks. |

## Harness CLI

| Command | Meaning | Writes? |
| --- | --- | --- |
| `harness init [PATH]` | Install a clone-local baseline without overwriting project files. | Yes |
| `harness init [PATH] --tracked` | Install a commit-ready project baseline instead. | Yes |
| `harness init [PATH] --dry-run` | Preview initialization. | No |
| `harness init [PATH] --apply` | Initialize and install managed runtime projections. | Yes |
| `harness plan [PATH] [--json]` | Preview creates, updates, removals, or drift conflicts. | No |
| `harness apply [PATH]` | Apply a conflict-free projection plan and record fingerprints. | Yes |
| `harness status [PATH] [--json]` | Compare managed files with desired state. | No |
| `harness norms validate [PATH]` | Validate the configured norm library. | No |
| `harness norms resolve [PATH] [SCOPE OPTIONS]` | Preview the stable model-facing norm bundle. | No |
| `harness validate [PATH]` | Validate a repository. | No |

| `harness doctor [--json]` | Inspect local prerequisites. | No |
| `harness eval` | Show the current eval scaffold. | No |

### Initialize another repository

The inspect-first workflow is:

```bash
cd /path/to/project
git init
harness init
harness plan
harness apply
harness status
```

Use `harness init --apply` for the same initialization plus immediate apply. Initialization
defaults to local mode and vendors:

- a concise always-loaded `AGENTS.md`;
- private `.harness/docs/` indexes and product, research, design, decision, experiment, runbook,
  and status files;
- the shared `norms/` index and complete current norm tree;
- a private `.harness/evals/` case structure;
- `harness.toml` and ignored repository-local state paths.

The harness records only paths it created and writes a scoped block to `.git/info/exclude`.
Ordinary user rules in that file are preserved, existing project files are never added to the
block, and default initialization leaves `git status` clean. Because this exclusion file is local
to the clone, initialize Git before running local mode.

Use the project-owned mode when teammates or CI should receive the baseline:

```bash
harness init --tracked --apply
```

Tracked mode removes only the harness-managed exclude block and places documentation and evals in
root-level `docs/` and `evals/`. Switching modes never overwrites existing files.

Every vendored file becomes project-owned. Initialization skips an existing file even when the
bundled baseline differs. It upgrades only byte-identical files generated by a known older harness
version; repeat initialization is otherwise idempotent.

The current generated OpenCode projection lives only at
`.opencode/plugins/awesome-harness/index.ts`.

If that generated file existed before the harness claimed it, or its bytes changed after apply,
the next plan reports `CONFLICT` and apply refuses to overwrite it. To remove the generated plugin,
set `runtimes.opencode.enabled = false`, inspect `harness plan`, and run `harness apply`; removal is
allowed only while the installed fingerprint still matches.

### Author and inspect norms

New norm files use the format in `docs/specs/norm-library.md`. Initialization copies all three
current shared Python norms, but they remain draft scaffolds and therefore create no active policy.
Validate and preview a scope with:

```bash
harness norms validate
harness norms resolve --area backend --language python --task implementation --path src/api.py
```

Drafts are excluded unless `--include-drafts` is supplied or `norms.include_drafts` is deliberately
enabled in `harness.toml`. Model-facing output omits TOML frontmatter and sorts norms by stable ID.

### Cliff status

`harness.toml` contains the Cliff character limits from the paper plus two explicitly experimental
harness hypotheses: a 60% trigger and eight recent turn pairs. Cliff is disabled by default. The
runtime-neutral transformer is implemented and tested, but OpenCode's current public compaction
hook cannot return a structured replacement message window. The installed plugin therefore does
not mutate history or claim to provide Cliff yet. See `docs/specs/cliff-compaction.md` and
`docs/research/opencode-cliff-adapter.md` before changing that gate.

## Superset

New Superset workspaces run `uv sync --extra dev` through `.superset/config.json`.

If workspace setup fails:

1. Confirm `uv --version` works in the workspace terminal.
2. Run `uv sync --extra dev` manually and retain the complete error.
3. Run `uv run harness doctor --json`.
4. Do not add credentials to the shared Superset config.

## OpenCode

The harness currently pins OpenCode `2.2.1`. Install the exact tested version with:

```bash
npm install --global @opencode/cli@2.2.1
```

Verify the real executable behind any Superset wrapper:

```bash
opencode --version
uv run harness doctor --json
```

Connect a provider interactively with `opencode auth login`, or launch the TUI and use `/connect`. Credentials are user-local and must never be committed to this repository.

### Learning checkpoint

- **Why pin it?** Compaction, session storage, plugins, and permission events can change between runtime releases.
- **What does Superset do?** Its `opencode` wrapper adds lifecycle integration, then delegates to the real OpenCode executable.
- **How do I prove the setup?** Both `opencode --version` and the `opencode` section of `harness doctor --json` must report `2.2.1` with status `match`.
- **Teach-back:** If the wrapper exists but the underlying executable is missing, why is checking only `which opencode` insufficient?
